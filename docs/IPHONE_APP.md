# iPhone companion app: what's actually buildable

Scoping notes. The goal is a small iPhone app that feeds our launcher directly, over Bluetooth,
without depending on the Rokid companion app and without a continuous hotspot.

## The key decision: our own BLE channel, not Rokid's

Rokid's glasses expose a BLE GATT server (service `00009400-…`) that the Rokid iPhone app talks to,
framed in Rokid's `Caps` format. We could impersonate that, but it buys us nothing: the data on it
(nav maps, weather) is generated by the Rokid app, which we are trying to not depend on.

Instead, **our launcher runs its own BLE GATT server** on the glasses. An Android app can do this
(`BluetoothManager.openGattServer` + `BluetoothLeAdvertiser`) independently of Rokid's system one;
the chipset already supports peripheral mode, since Rokid's assist server advertises. Our iPhone app
is the BLE central (`CoreBluetooth`).

Consequences:
- We define the service UUID, characteristics and payload format. No Caps, no reverse engineering.
- **No MFi certification.** MFi is only needed for the classic-Bluetooth (SPP/iAP) accessory path.
  A custom BLE peripheral that an iOS app scans for and connects to is unrestricted.
- Coexists with the Rokid app. The glasses hold two logical connections: Rokid's app ↔ Rokid's
  service, our app ↔ our service, over the same physical link. Both stacks multiplex this.
- Bluetooth LE, low power, always available away from home. Hotspot Wi-Fi stays optional, used only
  for the occasional large sync (see phase 3).

## What the app can do, by value and effort

### Phase 1 — the founding problem: pick which iPhone calendars sync
This project started because Rokid mirrors *every* iOS calendar, including hidden ones, and its feed
carries no calendar names so it can't be filtered. An iPhone app with **EventKit** reads exactly the
calendars the user ticks and pushes only those events over BLE to our launcher. This is a cleaner
fix than all three earlier options (the Apple Shortcut, iCloud CalDAV on the backend, Rokid's
unfiltered feed): native calendar picker, no server round-trip, works offline over Bluetooth.

Low bandwidth (a week of events is a few KB), so it is the ideal first payload and proves the whole
channel end to end.

### Phase 1 — custom notifications and reminders
EventKit reminders and a share extension let the app push arbitrary lines to the HUD's Messages
panel: a reminder, a note, "leave in 10 min". Complements the Rokid ANCS notification mirror we
already receive.

### Phase 2 — navigation destination hand-off
A share extension on the iOS share sheet (so "Share → HUD" from Google Maps, Apple Maps, a contact,
a pasted address) posts a destination to the launcher over BLE. The launcher can then start Rokid's
own navigation with it, removing the "open Rokid app, pick nav, type address" dance. This is the
realistic version of the Google-Maps-to-glasses idea; it hands over a destination, not a live route.

### Phase 2 — settings and profile sync
Mirror the backend settings page in the app, pushed over BLE, so the glasses are configured from the
phone with no Wi-Fi and no browser.

### Phase 3 — map tiles over BLE (optional, harder)
The user is open to BLE map pushing. It is feasible: Rokid's own app already streams `Nav_Map_Data`
byte arrays over BLE at ~1 Hz, so the hardware sustains it. Our app would fetch a small map tile
(the phone has internet), recolour it to the HUD green ramp (`MapTint` already does this on the
glasses side, or do it on the phone), compress, chunk over BLE, and the launcher renders it. This is
real work and bandwidth-bound (BLE practical throughput is ~10–100 kbps; a 20 KB tile at 1 Hz is
tight but within Rokid's proven envelope). Do it last, only if phases 1–2 land well.

## The BLE link design

One service, three characteristics, length-prefixed JSON. We own both ends, so keep it trivial.

```
Service   6E5D0001-…                      (our own 128-bit UUID)
  Write   6E5D0002-…  write / write-no-response   phone → glasses
  Notify  6E5D0003-…  notify                      glasses → phone
  Info    6E5D0004-…  read                         protocol version, launcher version
```

Framing: `uint32 length` + UTF-8 JSON, split into MTU-sized chunks; the receiver reassembles by the
declared length. A message is `{ "type": "...", "seq": n, "data": {...} }`, e.g.
`{"type":"calendar","data":{"events":[…]}}`, `{"type":"navto","data":{"lat":…,"lon":…,"label":…}}`,
`{"type":"note","data":{"text":"…"}}`. Binary payloads (a map tile) go as a base64 `data` field or a
second binary characteristic. No auth needed on a paired link for v1; add a shared secret in the
`Info` handshake if we ever want it.

## Coexistence and connection questions to confirm on-device

1. Whether the glasses' controller allows our advertiser/GATT server to run while Rokid's is active
   (expected yes; two advertisers, one shared GATT db). Verify with `BluetoothAdapter.isMultipleAdvertisementSupported`.
2. Whether iOS lets our app and the Rokid app both hold the glasses peripheral (expected yes; iOS
   multiplexes per-app CBCentralManager sessions).
3. Background behaviour: iOS CoreBluetooth central can run in the background with the
   `bluetooth-central` mode, so pushes continue with the app backgrounded; confirm reconnection
   after the app is jetsammed (state restoration).

## Build path

- **Prototype**: a launcher `BleServer` service (Android peripheral) + a throwaway SwiftUI app that
  connects and pushes one calendar event. Proves the channel.
- Sideload from the Mac with a free Apple ID (re-sign weekly) or a paid account (yearly). ~200–400
  lines of SwiftUI for phase 1.
- Then EventKit calendar picker, then the share extension.

## What stays out

- Continuous map streaming over *hotspot* — the user ruled out a continuous Wi-Fi dependency.
- The classic-SPP path Rokid also exposes — needs MFi from iOS, so we use BLE instead.
- Reimplementing Caps for the iPhone — unnecessary once we run our own BLE service.
